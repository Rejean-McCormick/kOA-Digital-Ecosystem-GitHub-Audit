# Evidence discovery, Git provenance, and progress tracking — v0.12.0

## Scope and explicit limits

This release enhances **private, dated evidence campaigns**. It does not scan all files, execute tests, infer security defects, assert readiness, or publish evidence to GitHub. All local source repositories remain read-only. Previously created campaign archives and checksums are supported without migration.

## Windows workflow

1. Extract the application ZIP and launch `kOA_GitHub_Audit_Launcher.pyw`.
2. In **Campagnes datées**, select an existing `audit.json` from a previous **local** observation when available. It can supply the original local clone locations and historical commit identities; no audit is rerun.
3. To produce **new static metadata measurements**, choose **Mesurer ce clone** or **Mesurer clones de l'audit**. Git-only collection is the default; the optional `scc`, Lizard, Universal Ctags checkbox requires separate consent and installed executables. No project tests or code execute.
4. To find **existing tool-generated reports**, choose **Trouver rapports de ce clone** or **Trouver rapports des clones de l'audit**. The collector examines only exact report filenames in a short allowlist of likely directories. It verifies the clone's GitHub `origin`, recognizes JUnit, coverage or SARIF reports, and shows the detected documents before you approve any copying into the next private campaign.
5. Review those reports: test logs, SARIF and coverage documents **can contain sensitive local information**. Discovery returns only summaries; the **original bytes are copied into the private campaign only after your confirmation**. You may always decline and attach files individually.
6. Click **Créer une campagne figée**. It preserves report bytes, SHA-256, import timestamp, recognized report metrics, the manual qualification and practice registers, bundled engineering profiles, Kristal projection, available historical audit SHA and current Git metadata. If a discovered file changed since the preview, the capture is rejected until you review it again.
7. In **Écosystème → Ouvrir le centre de pilotage**, the local-only **Campagnes de conformité figées** section displays a summary of the most recent campaign, manual proof bars and a link to compare the last two captures. Select an application and click **Fiche figée · dernière campagne** to view dated documentation, clickable profiles, original evidence and the GitHub archive link pinned to the recorded SHA.

## Discovery is bounded, not a recursive source scan

- Directories: repository root, `reports`, `test-results`, `test_results`, `artifacts`, `coverage`, `build/reports`, `build/test-results`, `results`.
- Filenames: known JUnit XML variants, `coverage.xml`, `coverage.json`, and known SARIF filenames. Unsupported or unrecognized documents are not proposed.
- At most **8 recognized reports per repository**; at most **2 MB read per discovered report**, with higher manual attachment limits remaining available. Symbolic links, including symlinked ancestor directories, are not followed. Clone origin must match the selected inventory repository. Missing reports are *unknown/not supplied*, never failures.
- There is no shell, GitHub API, checkout, fetch, commit, push, test execution, container launch, or dynamic install.
- The discovery list does not export raw report data. Approved reports are **private**, and their contents can still include secrets. Always review before sharing an archive.

## Provenance and dates

Each imported evidence file has its own hash and import time. A report generated by the **kOA static collector** can declare the observed Git HEAD and capture time. The app compares that SHA to the pinned campaign Git reference, producing distinct values for matching, differing, alone, or unknown SHA references. **A matching SHA observation is not proof that an imported JUnit, coverage or SARIF report was executed at that version.** Pre-existing reports remain explicitly *unbound* unless you supply independent execution provenance.

Bundled Engineering Profiles from user-supplied snapshots retain their separate input snapshot provenance. A GitHub commit ZIP URL may stop working after history rewriting or deletion; a permanent source archive or protected release remains an independent retention responsibility.

## Progress charts and comparison

The local history shows dated profile **coverage**, attached report counts, report categories, manual practice reviews, and five **separate** manually supported qualification milestones. It compares added and removed evidence attachments by **content SHA-256 and report category**, not name or file count alone. A replaced JUnit report therefore appears as one report removed and one added rather than being quietly treated as unchanged. It also shows changes in the manual stages and changed Git references.

The main atlas loads status-only latest campaign data **from the localhost preview server**. GitHub Pages has neither the route nor access to the private archives. The atlas falls back safely to the public, profile-based view when not served locally.

Counts are **coverage of available evidence**, not a development completion rate, a weighted maturity score, an automatic certification or a security verdict. Reviews remain manual and scope-specific.

## Verification and operations

The release tests synthetic Git clones, limits, symlinks, mismatched remote identities, report recognition, immutable evidence copies, a changed-file rejection, comparison of two dated campaigns, the privacy of summary payloads, Tkinter initialization, and browser navigation with mocked localhost data. User Windows installations, repositories and remote GitHub downloads cannot be verified from the release test environment.

Existing local archives are kept under `%LOCALAPPDATA%\kOA-GitHub-Audit\campaigns\`; local collector metadata under `%LOCALAPPDATA%\kOA-GitHub-Audit\evidence_runs\`. Neither location is part of the application ZIP or the public Pages publishing allowlist.
