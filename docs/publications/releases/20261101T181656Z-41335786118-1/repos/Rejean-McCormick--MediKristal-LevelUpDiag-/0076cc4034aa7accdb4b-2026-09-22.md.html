# Status — LevelUpDiag-MediKristal

**Date:** 2026-09-22  
**Version:** 1.1.2  
**State:** Operational / validation suite ready  
**Default target:** `C:\mycode\MediKristal\MediKristal`

## Current state

LevelUpDiag-MediKristal is operational as both a CLI validation suite and a Windows Tkinter UI (`LevelUpDiag-MediKristal.pyw`). The UI preloads the MediKristal repository path above, while still allowing another repository directory or ZIP archive to be selected.

The suite contains the original LevelUpDiag diagnostic layers plus MediKristal-specific validation levels. Campaigns available are `baseline`, `software`, `delivery`, `release`, and `deep`.

## Suite validation

The suite's own regression tests currently pass:

- **15/15 internal tests PASS**
- Python modules and `.pyw` launcher compile successfully
- ZIP extraction includes zip-slip protection
- `fail-fast` persists a `result.json` for blocked levels
- suite manifest completeness and SHA-256 integrity are checked automatically
- UI target detection and default target path are covered by tests

## MediKristal validation profile

MediKristal-specific levels currently cover:

- `MK10` — repository identity and expected layout
- `MK20` — OpenAPI/contracts/traceability
- `MK30` — FastAPI runtime smoke validation
- `MK40` — Alembic migration validation
- `MK50` — packaging, wheel, SBOM and manifest checks
- `MK60` — reproducibility of generated delivery artifacts
- `MK70` — verification of documented validation claims
- `MK80` — deployment/static production-hygiene checks

## Last observed MediKristal result

Using the supplied `MediKristal_final_complete.zip` snapshot:

- application tests: **73 PASS**
- OpenAPI/runtime/migrations: PASS in the exercised checks
- `MK50`: WARN because original source archives were not available to independently revalidate every archive hash
- `MK60`: FAIL because generated validation artifacts were not fully reproducible; a fresh documentation validation produced **208 PASS** while delivery material claimed **211**
- `MK70`: FAIL because fresh coverage measured **87.24% global / 86.25% API**, while the delivery documentation claimed **91% global / 86% API**; the documentation count discrepancy was also detected
- `MK80`: WARN because static deployment checks pass, but Docker/PostgreSQL runtime execution was not available in the validation environment

These failures are evidence/claim consistency failures, not a claim that the 73 MediKristal application tests failed.

## UI status

The Windows UI supports:

- repository-folder or ZIP target selection
- default target `C:\mycode\MediKristal\MediKristal`
- campaign selection
- configurable worker count
- `fail-fast`
- per-level progress events
- verdict/result table
- finding details and evidence access
- summary copy/export workflow

The UI runner callback has been exercised on a real `baseline` campaign. Full visual interaction is not automated in the headless validation environment.

## Known limitations

- Docker/PostgreSQL live deployment checks require a machine with those services available.
- Git-related context can report WARN when validating an extracted archive that no longer contains `.git` metadata.
- External MediKristal partner/FHIR capabilities cannot be proven by LevelUpDiag unless the target repository provides the corresponding profiles, credentials, fixtures or test endpoints.
- Reproducibility checks intentionally fail when documented evidence cannot be regenerated from the current repository state.

## Next validation work

Priority follow-ups are to keep the suite strict rather than suppressing evidence drift:

1. Re-run `release` after MediKristal regenerates its documentation validation report and coverage claims.
2. Exercise `MK80` on a host with Docker and PostgreSQL available.
3. Add external-integration validation levels only when concrete MediKristal connector contracts become available.
4. Keep `suite-manifest.json` synchronized so every shipped file remains hash-verifiable.
