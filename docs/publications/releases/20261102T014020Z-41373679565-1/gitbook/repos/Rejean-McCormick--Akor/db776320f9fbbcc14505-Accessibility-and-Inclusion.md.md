# Accessibility and Inclusion

**A child can participate differently and still belong to the same team.** Akor should encourage shared work without making disability, reading difficulty, language background, absence or pace a visible label.

## Design starting points

Kontexte already describes three **design variants**: `accompagne`, `standard`, and `approfondi`. They are not diagnostic categories and are not a fully implemented adaptation engine. Selecting supports for actual learners requires teacher judgment, secure private delivery and review.

The same fictional role can use different scaffolding, languages, input methods, or task granularity while maintaining the group's shared goal. However, changing an academic learning target is a pedagogical decision, not a side effect of an accommodation flag.

## Interaction access

- Do not make spoken language the only way to make a contribution.
- Provide typed, visual or teacher-mediated alternatives where compatible with the objective.
- Support turn taking without mandatory speed pressure.
- Allow keyboard access, focus visibility, meaningful labels and screen-reader-friendly status messages.
- Avoid interactions that rely only on color or drag-and-drop.
- Let students request help privately and without penalty.
- Plan for unreliable Wi-Fi, one shared classroom device or absent partners.

## Fair role design

Every participant must have **meaningful agency**, including learners who need more time or support. A learner should not be assigned a decorative role because they are struggling, nor be made responsible for every difficult decision because they are quick.

If a teammate is absent, the teacher can authorize a fallback and explain it to the group in neutral language. The software must not impersonate an actual child or produce fabricated learning evidence.

## Privacy of supports

Never expose a learner's medical, disability, accommodation, mastery, or intervention profile to peers in mission state, team chat, URLs, logs or public exports. A role's visual theme must not encode private support levels. Teachers should see the minimal evidence needed for teaching.

## Acceptance activities

Test with keyboard, screen readers where feasible, small screens, communication alternatives, recovery after disconnect, and educator review. A checklist is not equivalent to user validation with appropriate safeguards.
