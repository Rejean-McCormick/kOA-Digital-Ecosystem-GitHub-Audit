# Capability Status

> **Authority and status:** This wiki is an explanatory navigation layer. The repository contracts, accepted ADRs, normative documents, and executable validators remain authoritative for kOA-Linux Operating System. Public initkoa.org pages explain the wider kOA ecosystem and the product capabilities provided by its independently documented subsystems.

## Status vocabulary

| Status | Meaning |
| --- | --- |
| Publicly described | The capability is described on initkoa.org or an official public context pack. |
| Boundary specified | The kOA-Linux repository defines how the subsystem integrates or operates. |
| Target architecture | The required behavior is specified but needs implementation evidence. |
| Profile-dependent | Availability depends on the selected deployment profile and installed artifacts. |
| Experimental | The public source explicitly presents the system or feature as conceptual or experimental. |

## Capability matrix

| Capability | Public description | kOA-Linux boundary | Production claim |
| --- | --- | --- | --- |
| Siloed sovereign operation | System-of-systems and offline/portable architecture | Strongly specified | Requires deployment evidence |
| Kristal portable knowledge | Core public technology | Runtime and artifact lifecycle specified | Requires implementation and conformance evidence |
| Ariane assisted navigation | Public technology | Local boundary and optional external voice ADR | Requires subsystem implementation evidence |
| Orgo roles, tasks and closure | Core public platform | Subsystem boundary specified | Requires Orgo deployment evidence |
| Konnaxion public coordination | Core public platform | Subsystem boundary specified | Requires Konnaxion deployment evidence |

| SenTient reconciliation | Public conceptual architecture | Optional isolated boundary | Explicitly not production-ready |
| Offline operation | Core design commitment | Profiles, operations and lifecycle specified | Must be tested per profile |
| Collective governance to execution | Cross-system design | Governance and boundary components specified | End-to-end integration evidence required |
