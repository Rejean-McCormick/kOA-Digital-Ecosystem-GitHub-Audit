# Architecture and data flow

Skope is a **standalone Python package** plus a browser UI. It depends on pre-existing *data products*, not on importing the EncyK source checkout.

```text
Browser (index.html + vanilla JS/CSS)
          |
          | loopback HTTP /api/*
          v
skope/api.py   (ThreadingHTTPServer)
  |-- db.py                ---> finalized compact Wikidata SQLite (READ ONLY)
  |-- scope.py / geography.py ---> bounded preview, convergence, annotations
  |-- scope_profiles.py    ---> scopes/*.json (validated catalog)
  |-- kristal_registry.py  ---> workspace manifests (READ ONLY)
  |-- massive.py           ---> 30_working/skope-large-scopes/<job>/
  |-- extraction.py        ---> preverified dump + existing locator/sidecar (READ ONLY)
  |                             |-> 30_working/skope-extractions/<job>/
  |                             `-> 20_evidence/scope-snapshots/<scope>/wikidata-*/
  |-- author_campaign.py   ---> Catho roster -> matched people, P50 works, QIDs
  |-- reconciliation.py    ---> 30_working/skope-reconciliation/<job>/decisions.sqlite
  |-- reconciliation_batch.py -> ranking, progress, proposals, reviewed CSV
  `-- export.py            ---> non-canonical EncyK proposal/large-scope plan ZIP
```

## Native portfolio CLI (added in 0.15.0-alpha.1)

The portfolio controller is **not** a browser endpoint. `python -m skope portfolio` dispatches via `skope/cli.py` to `skope/portfolio.py`:

```text
v11 ZIP / project folders  (READ ONLY)
   |--- portfolio.inventory() ---> separate --work/portfolio.sqlite
   |--- portfolio.discover()  ---> db.py / compact index (READ ONLY)
   |--- suggest_drafts() / approve_review() ---> unverified or reviewer-attested seeds
   |--- portfolio.acquire()  ---> extraction.py / fastio.py / verified full dump (READ ONLY)
   |                                `-> source chunks + manifests in --out
   `--- portfolio.propose()  ---> complete Wikidata claim proposals and related QIDs

     [diK review / Authoring Kit publication: not integrated in this alpha]
```

The portfolio reuses existing source readers and verification rather than maintaining a separate Skope–diK bridge. Its working SQLite database stores input SHA-256 and index identity to prevent accidental mixing of runs. A Q/P candidate from the index does not establish a KQ/KP identity. The original Wikidata statement contains source qualifiers and references that the discovery index omits. **No portfolio operation writes canonical Kristal files.**

For the release-specific contract see [Portfolio Enrichment](Portfolio-Enrichment).

## Logical layers

**Read/query (`db.py`):** SQLite opened in `mode=ro` with required tables `entity`, `name`, `entity_edge`, `meta`; `meta.complete` must be true. Entity identifiers and compact edges are optimized for discovery and have no source `statement_id`.

**Scope selection (`scope.py`):** recipe validation; radial traversal preserving first-hop branch provenance; capped preview; one external-convergence candidate wave; optional geography evidence annotations.

**Disk-backed collection (`massive.py`):** SQLite-backed `selected` and traversal queue, a job status table, pause/resume and eventual `selected-qids.jsonl`; never silently runs from a profile refresh.

**Full-source preservation (`extraction.py` + `fastio.py` + `scope_common.py`):** checks dump identity records and locator readiness, seeks requested source entities, validates QIDs, generates compressed JSONL parts and hashes, and promotes complete batches to an evidence snapshot.

**Review (`author_campaign.py`, `reconciliation.py`, `reconciliation_batch.py`):** separate roster, offline candidate search and auditable decisions. Working decisions never rewrite the source roster or Kristal canon.

## Trust boundaries

```text
Aggregated discovery index    != complete Wikidata claim provenance
Scope recipe                   != an executable script
Graph preview                  != full scope inventory
Ranked candidate               != verified personal identity
Source JSON record             != externally corroborated assertion
Working proposal               != approved canonical content
```

## Runtime and persistence

The HTTP service uses `ThreadingHTTPServer`, but its address/Host checks restrict deployment to loopback. Long-running inventories and extractions use Python daemon threads and persistent disk status. Server restarts can mark unfinished work interrupted; resume must pass job-specific safety checks. There is no external queue or automatic distributed scheduler.
