# SEC-27 — Provenance, Not Just SBOM

## Core principle

An SBOM says what components are present; provenance says how an artifact was built, from what source and by which builder. You need both to reason about tampering.

## Security invariant

Production artifacts SHOULD carry verifiable provenance tying immutable artifact digest to source revision, build definition, builder identity and relevant inputs. Consumers verify provenance against policy before admission.

## Senior architecture

Adopt SLSA v1.2 concepts: Build provenance and, where practical, Source provenance/verified properties. Target hosted, isolated build infrastructure for high-value releases. Store attestations with the artifact and verify them at promotion/admission, not only during CI.

## Application to the supplied ecosystem

Konfid CI already creates an SBOM, while its production docs explicitly defer image signing/provenance/admission to the platform. The next step is to make that external requirement concrete and machine-verifiable for every release channel and Runtime Pack.

## Failure modes / anti-patterns

- SBOM treated as proof artifact came from trusted source.
- Provenance generated by the same untrusted build step that could alter it.
- Attestation exists but deployment never verifies it.
- Mutable tags used as subject identity.
- Builder identity too broad to distinguish secure/insecure modes.

## Evidence that proves the control

Given a running digest, tooling can retrieve and verify provenance, source revision and builder identity. Admission rejects missing/untrusted provenance. Provenance signer is isolated from tenant-controlled build steps at the targeted assurance level.
